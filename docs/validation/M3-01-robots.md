**Stretch 3 失败的原因：**组合后编译时报“Error opening file '…/hello_robot_stretch_3/hand_crush.png'”，正确路径应是 `…/assets/hand_crush.png`。Stretch 用 `compiler assetdir="assets"` 指定资源目录。MuJoCo 4.0.1 在组合后编译时，贴图按组合模型（父模型）的 `texturedir` 查找，没有用子模型自己的目录。网格按子模型的 `meshdir` 查找，所以 G1、Go2 正常。这正是 M2-09 报告中“组合的子模型通过外部文件引用网格”这项风险，在第一台带贴图的机器人上暴露出来。

**修正：**`composeWorld` 在组合前把每个子模型中网格、贴图、高度场、蒙皮的相对文件路径改成绝对路径（按子模型的目录与 meshdir / texturedir 展开）。MuJoCo 拼接路径时会原样保留绝对路径，结果不再依赖它在组合后使用哪个模型的目录设置。`robots.import` 即为回归测试。

**第二次运行（2026-11-23）：**结果与第一次相同，Stretch 3 仍报同样的错误。查看器中打开时报的是另一张贴图 `serial.png`。
- 第一次修正按 `mjSpec` 中的 `compiler.texturedir` 展开路径。对照 MuJoCo 4.0.1 源码后发现：解析 `<compiler assetdir="assets">` 时，先把 assetdir 写入 meshdir 与 texturedir，**随后按属性表读取 compiler 的其余属性，会把没写的 meshdir / texturedir 重置为默认值（空）**。解析器在读文件时用掉了 assetdir，`mjSpec` 中不一定留有它。因此第一次修正得到的仍是 `<模型目录>/hand_crush.png`。
- G1、Go2 用 `meshdir` 显式写出，不受影响。

**第二次修正：**依次尝试三个候选：`mjSpec` 中的目录设置；直接从 MJCF 文本（含 `<include>` 的文件）读出的 `assetdir` / `meshdir` / `texturedir`；模型目录本身。取第一个存在的文件，改为绝对路径；都不存在时保持原样，由 MuJoCo 报告。测试另外记录“不经组合、直接由 MuJoCo 加载 Menagerie 的 scene.xml”是否成功，用来判断 MuJoCo 4.0.1 单独加载时是否也有这个问题（只记录，不判定）。

**第三次运行（2026-11-23）：查明真正的原因。**新增的对照项显示，**不经组合、直接由 MuJoCo 加载 Menagerie 的 `scene.xml` 也同样失败**，可见问题与组合无关。核对后发现，`assets/robots/hello_robot_stretch_3/assets/` 中根本没有这 12 张 PNG 贴图：

- **原因是锁定记录漏了文件。**生成 `robots.lock` 时，本意是排除各目录顶层的预览图，用的是 `find ! -path "<目录>/*.png"`。但 `find -path` 中的 `*` 也匹配 `/`，结果把 `assets/` 子目录中的贴图一起排除了。锁定记录只有 187 个文件，缺了 Stretch 的 12 张贴图，准备脚本因此没有复制它们。
- **前两次的诊断都是错的。**“组合后按父模型目录找贴图”“assetdir 不保留在 mjSpec 中”这两个判断，都没有先确认文件本身存在，就去分析 MuJoCo 内部。两次修改已经全部撤回，`mujoco_world.cpp` 恢复到 M3-01 之前的样子。M2-09 报告中“子模型资源路径”的风险仍然有效，但本例并未触发它。

**第三次修正：**重新生成锁定记录，只排除 `<目录>/*.png`（顶层），共 199 个文件，其中贴图 12 张。用户的原件与新记录 199/199 一致。准备脚本会把缺少的贴图从 `ROBOTS/` 复制过来。保留“直接加载 scene.xml”的对照记录，它在这次排查中起了关键作用。

**教训：**素材出错时，先确认文件存在、内容一致，再分析加载器。锁定记录的生成命令，也要核对文件数是否与源目录一致。
