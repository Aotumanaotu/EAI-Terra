# M1-15 性能监视图表

> 状态：**已实现并通过基线验证、待验收**（2026-11-23 第六次运行全部通过，第 4 节）。来源：用户 2026-11-23 建议（“统计数据形成动态图表，特别是显卡显存占用率和 CPU 占用率；不算核心功能”）。开发计划 M1-15（P2），在 M1-11 阶段验收前完成。

## 1. 内容

统计面板底部新增可折叠的“性能图表”，四张随时间向左滚动的折线图（与属性滑块同一视觉风格：圆角框、网格线、右上角图例与当前值）：

| 图表 | 序列 | 来源 | 刷新 |
| --- | --- | --- | --- |
| 帧时间 | 整帧、显卡（虚线为 16.7 ms） | 主循环帧间隔；GPU 时间戳总和（M1-10） | 每帧，保留 600 帧 |
| CPU 占用 | 本进程、整机（0–100%） | Linux `/proc/self/stat`、`/proc/stat` 两次采样的增量 | 每 0.25 秒，保留 60 秒 |
| 显存 | 已用（纵轴上限为总量） | NVIDIA `GL_NVX_gpu_memory_info`（总量与可用）；AMD `GL_ATI_meminfo`（只有可用量，不画图） | 每 0.25 秒 |
| 进程内存 | 常驻内存 | `/proc/self/statm` | 每 0.25 秒 |

统计表另显示 CPU 逻辑核数与显存数据来源。数据不可用时（如 llvmpipe 没有显存查询扩展、非 Linux 平台）明确显示“不可用”，不显示为 0。GPU 利用率（%）需要 NVML，未做。

## 2. 实现

| 位置 | 内容 |
| --- | --- |
| `terra/core/time_series.hpp` | 固定容量滚动序列（从旧到新访问、最小 / 最大 / 平均） |
| `terra/core/system_monitor.hpp` | `/proc` 解析纯函数（进程名含空格与括号时按最后一个 `)` 计字段）、占用率公式（计数回退或无增量时为空）、`SystemMonitor::sample` |

## 4. 验证记录

开发机：未编译、未运行（按约定）。已做：新增界面文字 392 个字符字形齐全；5 个变异锚点唯一匹配；脚本 `bash -n`。

**基线机器第一次运行（2026-11-23）**：渲染关闭 39/39 通过；渲染开启的三种构建**编译失败**：`widgets.cpp` 调用了 ImGui 1.93 中已删除的 `ImDrawList::AddPolyline(points, n, col, flags, thickness)`——1.92.8 起该函数（以及 `AddRect`）的 `thickness` 与 `flags` 参数对调，旧顺序被标为 `= delete`。变异测试中前 4 项均被发现，第 5 项因同一编译错误未判定。

**修正**：改为新顺序 `AddPolyline(points, n, col, 1.5f, ImDrawFlags_None)`。同时对照 1.93 头文件复查了本次新增的全部绘制调用：`AddRect` 只传 4 个参数，落在新签名上；`AddRectFilled`、`AddLine`、`AddText`、`PushClipRect`、`CollapsingHeader` 的签名均未变。开发机此前的接口核对漏查了“已删除的旧签名”，以后对绘制列表 API 一并核对 `= delete` 的重载。

**第二次运行（2026-11-23）**：渲染关闭 39/39；开启 Debug / Release **56/57**、ASan 图形 10/11——唯一失败为 `graphics.render_pbr` 的“llvmpipe 显存查询为空”：**llvmpipe 也声明了 `GL_NVX_gpu_memory_info`，但总量与可用量都返回 0**（查看器自检在 Xvfb 中打印“总量 0 MB”），我原先假设它不声明该扩展。其余全部通过：变异 **5/5**；三张参考图逐像素一致；`core.system_monitor` 实测本进程 4.2%、整机 9.5%、常驻 3.4 MB、24 个逻辑核；RTX 5060 显存总量 8151 MB、可用 4904 MB；性能图表数据已记录；展示 47.5 秒、59.9 FPS。

**修正**：驱动报告的总量（NVX）或可用量（ATI）≤ 0 时视为不可用（返回空，界面显示“不可用”）。测试说明同步更新。

**第三次运行（2026-11-23）**：结果与第二次相同（56/57，同一项失败），但查看器自检此次打印“显存：当前驱动不提供查询”。单独运行该测试（`ctest -R '^graphics\.render_pbr$' -V`）得到原始值：**llvmpipe 的 NVX 查询报告“总量 526344 MB、可用 526344 MB”**。llvmpipe 在三处给出了三种结果（0、空、约 514 GB），说明它通过这个扩展报告的根本不是显存，靠检查数值无法可靠排除。

**修正**：按渲染器类型判断，而不是按数值判断——软件渲染器（渲染器名含 llvmpipe、softpipe、swrast、SWR）没有专用显存，`gpuMemory()` 直接返回空；对硬件驱动保留数值检查（总量 ≤ 0、可用量 < 0 或大于总量时也视为不可用）。新增纯函数 `isSoftwareRenderer` 及其测试（llvmpipe、softpipe 识别为软件，NVIDIA、AMD 不是）。变异“显存为 0 时仍当作可用”在 llvmpipe 上已无法被发现（软件渲染器判断在前），改为“软件渲染器仍报告显存”。

**第四次运行（2026-11-23）**：全部测试通过——渲染关闭 39/39；开启 Debug / Release 57/57；ASan 46/46 + 11/11；三张参考图逐像素一致；查看器自检在 llvmpipe 上显示“显存：当前驱动不提供查询”。但变异 **4/5**：“软件渲染器仍报告显存”未被发现。原因同上：去掉软件渲染器判断后，结果取决于 llvmpipe 这次返回什么；变异运行时它返回的值恰好被数值检查排除，测试照样通过。依赖驱动返回值的测试无法稳定发现这个错误。

**修正**：把“原始值 → 显存”的判断抽成纯函数 `gpuMemoryFromReport(渲染器名, 扩展名, 总量 KB, 可用量 KB)`，`gpuMemory()` 只负责读取驱动后调用它。用固定输入测试：llvmpipe 报告约 514 GB（实测值）或 0 都为空；NVIDIA 8151 / 5100 MB 原样换算；硬件驱动总量 0、可用量大于总量为空；ATI 只报告可用量。变异锚点改到纯函数中的软件渲染器判断，现在由固定输入的检查发现，不再依赖驱动。

**第五次运行（2026-11-23）**：测试结果同第四次（全部通过，参考图逐像素一致）；变异 4/5——“软件渲染器仍报告显存”**编译失败，未判定**：去掉判断后 `renderer` 参数不再使用，`-Wunused-parameter` 在 `-Werror` 下报错。脚本问题，与产品代码无关。

**修正**：变异替换为 `(void)renderer;`。

**第六次运行（2026-11-23）：全部通过。**渲染关闭 39/39；渲染开启 Debug、Release + `-Werror` 57/57；ASan 非图形 46/46、图形 11/11；变异 **5/5**（每项 1 个检查失败）；三张参考图逐像素一致；`core.system_monitor` 实测本进程 4.2%、整机 5.6%、常驻 3.4 MB、24 个逻辑核；查看器自检在 llvmpipe 上显示“显存：当前驱动不提供查询”。真实 GPU 显存与图表展示已在第二、三次运行中确认（RTX 5060 总量 8151 MB）。
