# M5-02b glTF 环境导入：实现与验证

> 状态：**基线验证通过**（2026-11-27，第 4.3 节）。
> 设计见 [M5-01 设计稿](M5-01-scope-design.md) 2.1 节；分步原因见 [M5-02a 报告](M5-02a-elements.md)第 0 节。
> 素材：用户 2026-11-26 准备的 `blender/`，包括：
> - 110 kV 变电站：233 个顶层节点，51 万三角形；
> - 三层办公楼：248 个顶层节点，38 万三角形；
> - 两个场景都有 `manifest.json`，许可均为 CC0-1.0。

## 1. 用户能做什么

- **导入：**
  - 查看器：“文件 → 导入环境（glTF）…”，或把 `.glb` / `.gltf` 拖进窗口。导入到资源库目录的 `environments/<名字>/` 后直接打开；
  - 命令行：`terra_import --environment <glb> [--name 名字] [--output 目录] [--manifest 清单] [--collision boxes|hulls] [--max-boxes N] [--overwrite]`。导入后组合进物理世界并推进 0.2 s 检查，最后一行输出统计（JSON）。
- **输出：**
  - 每个顶层节点一个元素文件，外观引用原 glb 的该节点；
  - 一个场景文件，`models` 为空，`elements` 列出全部元素，放置位姿就是节点在 glTF 中的位姿；
  - 导入报告。
- **清单：**`blender/` 资产流程的 `manifest.json`，不指定时在 glTF 所在目录及其上一级查找。用到的字段：
  - 类别、可否移动、质量、许可；
  - 默认温度；
  - `thermal.parts`：按子节点的温度，成为元素的部件；
  - `inspection`：检查点，位置取节点网格包围盒的中心，拍摄距离与俯仰照抄。
- **用户的两个场景：**`scripts/assets/import_environments.sh` 把它们导入到 `assets/environments/`（不提交），并各写一个“Go2 巡检”场景：
  - Go2 放在清单推荐巡检路线的起点，朝向第二个点；
  - 机身 IMU；
  - Mid-360，正装在机身上方，带内置 IMU 与外观（第一次运行时是倒挂的，用户要求改为正装）；
  - 前方的 Lepton 3.5 热像仪。

  资源库启动时扫描 `assets/environments/`，四个场景都出现在“场景”分页。元素文件只由场景引用，不出现在“元素”分页。

## 2. 实现

| 项 | 做法 |
| --- | --- |
| glTF 读取 | `engine/import` 自带只读的 glTF 读取，不用 cgltf，不依赖图形，Headless 构建中也可用：<br>- .glb 与 .gltf（外部 .bin 或 base64）；<br>- 节点的 TRS 或矩阵、世界矩阵；<br>- POSITION 与索引 |
| 坐标 | glTF 为 Y 向上，Terra 为 Z 向上：(x, y, z) → (x, −z, y)。<br>元素坐标系为节点的旋转与平移。统一缩放进外观绑定的 `scale`，并计入碰撞体的尺寸；非统一缩放取平均并警告。<br>用户的变电站有 18 个节点带统一缩放（0.1～1.4，多为放进来的 Poly Haven 模型） |
| 盒体（默认） | 每个网格图元按共享顶点拆成互不相连的部分：索引相连，或位置相同（0.01 mm）。<br>每部分取三种包围盒中体积最小的：元素坐标系的轴对齐盒、网格坐标系的轴对齐盒、主方向（PCA）盒。<br>- 楼梯的 20 个踏步各一个盒体；<br>- 斜扶手、导线取细长的主方向盒，不会生成跨过整段楼梯的大盒子；<br>- 一个节点超过 24 个盒体时两两合并（每次取体积增加最少的一对）；<br>- 超过 512 个部分（如植物）时整个图元一个主方向盒；<br>- 最薄的半边长 5 mm |
| 凸包 | 类别或 id 含 `ramp` 的元素（坡道）、或 `--collision hulls` 时，每个网格节点导出一个 OBJ，由 MuJoCo 取凸包 |
| 部件 | `thermal.parts` 中的子节点成为部件，即焊在元素刚体上的子刚体 `<id>/<节点名>`，有自己的碰撞体、温度与分割 ID。<br>元素的外观绑定排除部件的节点（`VisualBindingSpec::excludeNodes`），部件另有绑定。<br>`dynamic` 元素不拆部件 |
| 温度的优先级 | 场景按实体全名写的 > 部件的温度 > 与元素本身相同（实例覆盖 > 场景 temperatures > 元素默认） |
| 场景文件 | 有 `elements` 时 `models` 可以为空 |

**估计规模**（开发机上用 Python 按同样的拆分规则统计，没有合并）：
- 变电站约 5800 个盒体，其中 30 个图元超过 512 个部分；
- 办公楼约 2200 个盒体；
- 合并后会更少，实际数量见第 4 节的运行结果。

碰撞体较多时，Mid-360 的射线检测会变慢。单帧耗时在 M5-09 中实测，需要时按开发计划 12.5 节做 GPU 加速。

## 4. 基线运行结果

### 4.1 第一次运行（2026-11-26）：界面文本 ID 重名，渲染构建失败（LOG-199）

### 4.2 第二次运行（2026-11-26）：测试全部通过

| 项 | 结果 |
| --- | --- |
| 测试 | 117 / 162 / 162 / 179，ASan 126 + 36 + 17，全部通过 |
| 变异 | 8/8 |
| 夹具 | 7 个元素、32 个盒体；箱子落到基座上 z = 0.4999 m |
| 变电站 | 233 个元素、4790 个盒体、120 个部件、83 个检查点；导入 369 ms，加载 393 ms，每步 0.633 ms |
| 办公楼 | 248 个元素、1841 个盒体、1 个凸包、14 个部件、21 个检查点；导入 281 ms，加载 181 ms，每步 0.433 ms |
| 查看器自检 | 8 个绑定全部可用，部件 75 °C，没有 GL 错误 |

**用户反馈：**
- 实际操作时只有 3～5 帧，GPU 没有占满，CPU 也不高；
- 控制向前，Go2 不动；
- 雷达不用倒置。

**原因（推断，数字是估算）：**Mid-360 的射线检测。
- MuJoCo 的 `mj_multiRay` / `mj_ray` 对每条射线检查全部几何体，只用包围球剔除；
- 在 8 个几何体的房间中，一帧（20,000 条射线）用了 3.5 ms（M5-11）。按同样的单价，变电站的 4846 个几何体约需 2 s；
- 雷达每秒扫 10 帧，单线程的仿真远远跟不上实时，于是丢弃仿真时间（Go2 走不动），帧率也被拖下来；
- 只有一个 CPU 核满载，所以总的 CPU 占用不高，GPU 是空闲的。

**修正（不需要 GPU）：**
1. **射线检测的包围盒树**（`engine/physics/backends/mujoco/src/ray_index.*`）：
   - 静止的几何体（焊在世界上的刚体）按世界中的轴对齐包围盒建一棵树，每条射线只检查与它相交的几何体；
   - 运动的与无界的几何体（机器人、可推动的元素、平面）逐个检查，先用包围球剔除；
   - 过滤规则与 MuJoCo 的 `ray_eliminate` 相同，求交调用同样的 `mju_rayGeom` / `mj_rayMesh` / `mj_rayHfield`，命中距离与原来逐位相同，读数不变（用户：最好不要影响效果）；
   - 模型中有 SDF 几何体时退回原来的做法。

   M4 的 2D 雷达与 M5-11 的 3D 雷达测试都经过这条路径，用来验证结果不变。
2. **渲染：**每个 glTF 绑定在加载时算好子树中的图元下标，每帧只按下标生成渲染项。原来每帧每个绑定都要遍历整个文件的 413 个图元。
3. **Go2 巡检场景的 Mid-360 改为正装**（机身上方 0.12 m）。

**新增检查：**`import.environment_assets` 在两个场景中从巡检起点发 20,000 条射线（Mid-360 一帧的数量），要求 100 ms 以内，两次结果逐位相同。
