# EAI Terra 开发计划书

> 当前执行阶段：**M3 准备**。M0（2026-11-19）、M1（2026-11-23）、**M2（2026-11-23，[M2-09 报告](../validation/M2-09-acceptance.md)）** 已验收。M3 任务分解草案见第 10 节，等待评审；参考机器人模型由用户下载（10.4 节）。本文定义开发任务和完成条件，不作为完成证明，实际进度与证据统一记录在[开发记录](DEVELOPMENT_LOG.md)。

## 1. 开发策略与环境

### 1.1 范围与阶段顺序

以[PRD](PRD.md)为需求来源，以[技术设计](TECHNICAL_DESIGN.md)为边界约束，按 M0 → M1 → M2 → M3 → M4 → M5 推进。只详细拆分当前 M0；后续阶段进入开发前再细化工作包。

M0 的结果是一套可构建、可测试、不创建任何图形上下文的物理闭环。首个可运行场景是自由落体立方体；机器人整机、自研渲染和编辑器均不是 M0 的交付条件。

### 1.2 第一阶段基线

| 项目 | 已确定方向 | 尚待验证或记录 |
| --- | --- | --- |
| 操作系统 / 架构 | Ubuntu 22.04 / x86-64 | 实际系统、CPU、内存和运行环境 |
| 语言 / 编译器 | C++17 / GCC | GCC 精确版本、编译选项、Debug/Release 配置 |
| 构建 | CMake / Ninja | 工具精确版本、最低兼容版本、目标划分 |
| 物理库 | MuJoCo 官方 C API | **目前没有已锁定或已验证版本**；候选版本通过 M0-02 后才锁定 |
| 测试执行 | 建议使用 CTest 统一入口 | 测试框架是否另选待定，不为框架选择阻塞最小测试 |
| 图形 / 机器人中间件 | M0 不引入 OpenGL 窗口、ROS2、Python | 图形和桥接依赖到对应阶段再评估 |

若后续发现已有明确版本记录，优先评估并沿用；不能直接把上游最新版本视为已验证版本。候选验证至少覆盖官方分发件来源与校验信息、C API 所需符号、头文件与运行库一致性、动态库查找、无图形运行、许可及再分发约束。失败则保留报告并比较其他官方版本。

**建议依赖策略，尚未确认：**优先支持显式指定本地官方库安装位置；构建阶段不隐式联网；优先评估官方 CMake 导出目标，缺失时再使用隔离的导入目标。版本、来源、校验值及运行时装载方式在验证通过后形成依赖记录。具体策略参见 `D-015/D-108`。

### 1.3 路径职责与当前边界

以下路径用于定位任务。当前 CMake 工程、最小 Core、Headless CLI、工程测试及环境验证记录已建立；Physics、物理测试夹具和状态契约仍为规划项。各路径只说明职责，不表示整套目标架构已实现；沿用根 README 的目录方向，不提前增加完整框架。

| 规划位置 | 用途 |

## 3. M0 详细工作包

### M0-01：开发环境与工程初始化

- **目标：**建立最小、可复现的 C++17 构建与测试入口，不加入图形依赖。
- **实施步骤：**① 清点系统和已有工具，仅在实际开发阶段处理缺项；② 确认 GCC、CMake、Ninja 的精确版本；③ 评审最小 Core/Physics/Headless 目标边界；④ 建立根构建入口及测试开关；⑤ 记录配置、构建和测试步骤。
- **涉及模块或文件：**规划中的 `CMakeLists.txt`、`cmake/`、`engine/core/`、`engine/physics/`、`apps/headless/`、`tests/`；依赖说明后续放在 `docs/validation/`。
- **前置依赖：**无。
- **预期交付物：**最小工程、环境清单、目标依赖关系、可复现操作说明。
- **验收标准：**干净构建目录能使用 Ninja 完成基础目标构建；C++17 配置生效；物理目标不要求窗口系统和图形开发包；文档明确哪些目标尚待后续任务接入。
- **风险和注意事项：**不能为“架构完整”创建所有后续模块；不能用当前宿主系统成功替代 Ubuntu 22.04 基线验证；依赖和编译工作只在后续实际开发任务执行。

### M0-02：MuJoCo 依赖集成

- **目标：**验证并锁定首个可用的官方 MuJoCo 版本，建立私有后端边界。
- **实施步骤：**① 检查已有版本决策，当前没有则列出候选；② 按确认的策略获取官方分发件并记录来源/校验值；③ 建立目标级依赖与运行库查找；④ 在隔离探针中核对头文件、运行库版本及所需 C API；⑤ 检查图形依赖是否进入运行前置条件；⑥ 验证通过后记录精确版本，失败则保留原因再选候选。
- **涉及模块或文件：**`cmake/`、`engine/physics/backends/mujoco/`、未来依赖验证报告。
- **前置依赖：**M0-01。
- **预期交付物：**依赖导入配置、版本兼容报告、锁定记录、私有后端最小骨架。
- **验收标准：**官方 C API 可链接且库可在无图形会话中装载；版本一致；依赖缺失或不匹配能定位；没有修改上游源码；应用公共头不泄露 MuJoCo 类型。锁定仍需通过后续场景回归，出现失败时重新评估。
- **风险和注意事项：**共享库查找、ABI/架构、打包差异及许可证；不得直接把官网或本机可见版本标为验证通过；不用自带 viewer 作为纯物理集成结果。

### M0-03：Headless 仿真程序

- **目标：**提供仅命令行的入口和受控退出流程。
- **实施步骤：**① 定义模型路径、步数/仿真时长、输出采样间隔等参数；② 校验互斥项、负数和无效路径；③ 连接 Terra 初始化、运行和释放入口；④ 约定机器可读状态流与诊断流分开；⑤ 在无显示环境启动，随后接入 04–06 的真实物理数据。
- **涉及模块或文件：**`apps/headless/`、`engine/core/`、参数与生命周期测试。
- **前置依赖：**M0-01、M0-02；完整运行能力在 M0-04–06 接入后验收。
- **预期交付物：**Headless 可执行入口、参数说明、退出码约定；JSON Lines 为建议输出形式，正式格式在 M0-06 确认。
- **验收标准：**缺少 `DISPLAY`、`WAYLAND_DISPLAY` 时可运行；不创建 OpenGL/EGL/OSMesa 上下文；非法参数非零退出；正常完成零退出；应用不调用 `mj_*` 或接触其数据结构。
- **风险和注意事项：**“不显示窗口”不等于“不依赖图形”；应检查链接/运行依赖并审查上下文创建路径，不能只依靠清空显示变量证明。

### M0-04：MJCF 模型加载

- **目标：**通过适配层建立一个可查询的物理世界。
- **实施步骤：**① 准备本文件定义的具名立方体/地面 MJCF；② 在后端封装 XML 解析编译、运行数据分配和初始化；③ 建立 Terra ID 到后端索引的私有映射；④ 初始派生状态同步后再发布初始快照；⑤ 覆盖文件缺失、XML 错误、引用资源缺失和释放路径。
- **涉及模块或文件：**`engine/physics/backends/mujoco/`、最小 `engine/core/` 类型、`assets/tests/falling_cube.xml`、加载测试。
- **前置依赖：**M0-02、M0-03。
- **预期交付物：**加载和初始化能力、具名测试资产、错误诊断、生命周期测试。
- **验收标准：**能按名称识别立方体及其自由关节；初始时间、位姿符合夹具；加载失败不留下可用半成品世界；数据资源先于模型释放；重复加载/释放不崩溃。
- **风险和注意事项：**M0 一个已编译 MJCF 对应一个世界的物理表示，不承诺动态增删；不把 MuJoCo body 下标当作长期实体 ID；MJCF 资产相对路径必须按明确定义解析。

### M0-05：物理仿真循环

- **目标：**固定步长推进、可停止、可重置，完成首个自由落体运行。
- **实施步骤：**① 固定并记录模型步长和求解配置；② 每步边界接收控制，在后端执行一步积分；③ 更新同一时间点的派生量，再发布只读状态；④ 按采样周期输出，停止条件依据步数或仿真时间；⑤ reset 后恢复初始状态、清除旧控制、重建初始观测并更新运行代次；⑥ 发现非有限数、意外重置或严重诊断立即结束并报告。
- **涉及模块或文件：**`engine/core/` 的最小运行循环、`engine/physics/`、`apps/headless/`。
- **前置依赖：**M0-04。
- **预期交付物：**固定步进和 reset 能力、首个立方体时间序列、停止及错误处理约定。
- **验收标准：**完成下节立方体基准；仿真时间按步长增长，不受输出或墙钟 sleep 改变；reset 后回到初始时刻和位姿；日志能区分新旧运行代次。
- **风险和注意事项：**积分后派生位姿可能未对应新时间，不能直接拼接旧位姿与新时间；刷新策略见技术设计。不得把追赶实时、可变步长或渲染调度加入 M0。

### M0-06：位置、姿态与关节状态读取

- **目标：**提供完整、含时间语义的 Terra 观测数据。
- **实施步骤：**① 按技术设计约定 SI 单位、坐标和四元数顺序；② 提取实体位姿、关节配置/速度及接触摘要；③ 补齐仿真时间、步序号、世界代次和诊断；④ 复制成 Terra 拥有的数据；⑤ 验证自由关节配置和速度维度不相同；⑥ 固定输出格式并验证旧快照不可被后续 step 改写。
- **涉及模块或文件：**`engine/core/` 公共数据契约、`engine/physics/` 转换逻辑、`apps/headless/` 输出、状态测试。
- **前置依赖：**M0-05。
- **预期交付物：**`PhysicsState` / `PhysicsSnapshot` 初版契约、状态输出样例、单位与坐标测试。
- **验收标准：**至少输出时间、实体 ID、位置、姿态、速度、关节状态和有效接触摘要；字段有限、姿态归一化；初始与步后数据处于同一观测时刻；不存在指向后端可变数组的公开视图。
- **风险和注意事项：**body 原点、质心、geom 与视觉网格原点不同；不能假定关节位置数组与速度数组等长，也不能把四元数导数当角速度。

### M0-07：Terra Physics 统一适配接口

- **目标：**收敛加载、初始化、步进、重置、控制、状态和快照能力。
- **实施步骤：**① 评审 `loadModel/initialize/step/reset/setControl/getState/getSnapshot` 初版语义；② 将加载和驱动能力保留在私有后端；③ 校验生命周期、ID、控制维度、单位和范围；④ 支持无执行器模型的空控制；⑤ 用简单单关节夹具验证非空控制；⑥ 检查公共头、链接关系和一个只消费 Terra 数据的测试调用方。
- **涉及模块或文件：**`engine/physics/` 的公共接口与私有适配、`engine/core/` 契约、`tests/physics/` 接口测试、`assets/tests/` 简单关节夹具。
- **前置依赖：**M0-04、M0-05、M0-06；其边界从 M0-02 就开始遵守。
- **预期交付物：**评审后的初版接口、生命周期与错误语义、控制和边界验证。
- **验收标准：**上层仅依赖 Terra 类型；非法顺序调用、未知 ID、NaN/Inf 和错误控制维度明确失败；合法控制改变参考关节响应；无执行器立方体正常运行；快照消费者不需要 MuJoCo 头文件。
- **风险和注意事项：**接口名称只是建议；不要承诺任意后端都具有相同模型和控制语义；控制输入按执行器定义，不能统一假定为力矩；M0 不需要第二后端。

### M0-08：基础物理场景测试

- **目标：**验证自由落体、碰撞稳定、状态读取、控制与 reset 的物理含义。
- **实施步骤：**① 首先运行立方体主夹具；② 对照碰撞前解析自由落体；③ 检查接触和末段稳定；④ 使用无重力夹具检查惯性状态；⑤ 用单铰链夹具检查关节读取及控制方向；⑥ 记录模型、配置、输出和失败诊断；⑦ 在固定配置下评审并冻结候选容差。
- **涉及模块或文件：**`assets/tests/`、`tests/physics/`、未来 `docs/validation/` 报告。
- **前置依赖：**M0-05、M0-06、M0-07。
- **预期交付物：**场景夹具、预期行为、带理由的容差表、可自动判断的测试结果。
- **验收标准：**下节主基准和辅助用例全部满足；每个失败能关联到夹具、步数、版本及状态字段；不以“程序没有崩溃”代替物理正确性。
- **风险和注意事项：**软接触存在允许穿透，不能要求位置绝对等于几何表面；有效接触不能仅由候选接触个数判断；不能通过随意增加阻尼或放宽容差掩盖错误。

### M0-09：自动化测试与验收

- **目标：**让另一名开发者能够复现 M0 并确认阶段完成。
- **实施步骤：**① 将加载、生命周期、状态、控制、物理场景及负向用例接入统一测试入口；② 在干净构建目录及无显示环境执行；③ 增加重复运行、连续运行和快照持有测试；④ 审查运行依赖和公共类型；⑤ 记录性能基线但不以候选性能门槛阻塞正确性；⑥ 汇总报告，逐项核对 DoD 并更新开发记录。
- **涉及模块或文件：**构建/测试配置、`tests/`、未来验证报告、[开发记录](DEVELOPMENT_LOG.md)。
- **前置依赖：**M0-01–M0-08。
- **预期交付物：**测试入口、可复现运行说明、M0 验收报告、剩余风险清单。
- **验收标准：**M0 DoD 全部满足；自动化失败返回非零状态并保留诊断；报告写明实际命令和结果；没有编造通过记录。
- **风险和注意事项：**CI 工作流和持续集成平台可后续接入，不能以平台未选定阻塞本地自动化；静态检查和编译成功不等于物理测试通过。GCC Sanitizer 和多配置覆盖为 P1 增强。

| 几何与质量 | 无限水平地面，表面 Z=0；立方体边长 0.2 m、质量 1 kg；body 原点、质心、几何中心重合 |
| 初态 | 中心位置 (0, 0, 1) m；单位姿态；零线速度和角速度；一个具名自由关节 |
| 环境 | 重力 (0, 0, -9.81) m/s²；无外力、无执行器、无空气阻力；具名地面和立方体；显式记录摩擦与接触参数 |
| 数值与求解 | 固定 dt=0.001 s，候选 Euler 积分；求解器类型、迭代数、容差、接触 margin/gap 等显式记录，不依赖未记录默认值 |
| 运行 | 5000 步，共 5 s 仿真时间；判定使用每步状态；展示输出可降采样；最后 0.5 s 为稳定窗口 |
| 输出 | 时间、步序号、世界/运行代次、实体 ID、位置、姿态 wxyz、线/角速度与坐标标签、自由关节配置/速度、有效接触计数、数值诊断 |

### 4.2 主场景判定

| 检查 | 候选判定方法 |
| --- | --- |
| 时间 | N 步后时间相对 N×dt 的误差 ≤ 1e-8 s；时间严格单调，无意外回退或自动重置 |
| 自由落体 | 在 t=0.05–0.20 s 的碰撞前采样，对比 z(t)=1−0.5×9.81×t²；位置误差 ≤ 0.005 m；初始阶段向下运动，平面内无显著漂移 |
| 发生接触 | 有效地面—立方体接触首次出现于候选 0.35–0.55 s 窗口；理想几何触地时间约 0.428 s，仅作解释，不要求数值求解精确落在该时刻 |
| 最终稳定 | 最后 0.5 s 内中心高度距 0.1 m 的偏差 ≤ 0.005 m；线速度范数 ≤ 0.01 m/s；角速度范数 ≤ 0.05 rad/s；窗口内持续存在有效地面接触。容差包含软接触允许穿透 |
| 数据有效 | 所有必需数值有限；四元数范数误差 ≤ 1e-6；姿态比较按旋转等价处理 q 与 -q；无非预期求解或数值异常 |
| 观测一致 | 时间、位姿、速度和接触摘要都对应声明的步后观测时刻；持有第 k 步快照不被第 k+1 步修改 |

精确有效接触判定在适配层按所选版本转换为 Terra 语义；不能仅以 MuJoCo 的总候选接触数大于零判定有支撑力，也不在首测中要求恢复理想刚性零穿透。

### 4.3 必须覆盖的辅助用例

| 用例 | 目的与通过条件 |
| --- | --- |
| 无重力、无初速度 | 多步后保持初始位姿，变化处于冻结容差内，排除坐标和初始化错误 |
| 单铰链与一个执行器 | 关节配置和速度维度/单位正确；已知小幅控制引起预期方向响应；对照执行器定义，不承诺通用控制性能 |
| 控制边界 | 空控制适用于无执行器夹具；未知 ID、维度错误、越界及非有限输入按约定拒绝，错误不能半写入当前命令 |
| reset / 再运行 | 同进程至少 20 次 reset/运行周期；时间、初态、控制和代次正确；同环境轨迹按候选 1e-9 数值容差比较，首次验证后冻结；不能据此宣称跨平台逐位确定性 |
| 连续运行 | 主夹具至少 60 s 仿真时间，无崩溃、非有限数或未报告自动重置；记录内存走势，不能仅凭一次观察宣称绝无泄漏 |
| 加载与调用失败 | 缺失/损坏 MJCF、资源缺失、初始化前 step、非法步长/步数：有明确错误和非零退出结果；后端不可恢复错误需在独立子进程用例中验证退出行为 |
| 生命周期与快照 | 重复加载/释放不崩溃；模型重载后旧 ID 明确失效；持有旧快照可安全读取，reset 后不与新代次混合 |
| 无图形与依赖边界 | 无显示会话可构建并运行；未创建任何图形上下文；应用与快照消费者不包含 MuJoCo 头文件；渲染模块不存在也能通过物理测试 |

### 4.4 性能测量方法

性能暂不设 M0 阻塞数值。分别测量“关闭逐步输出”和“开启规定采样输出”的耗时，记录 CPU、内存、系统、编译配置、版本、模型摘要、步长、步数、重复次数和预热方式。报告平均值、分位耗时及仿真时间/墙钟时间的实时因子；M1 起另测 GPU、分辨率和帧耗时。候选目标见 PRD 的 `NFR-03`，不能由简单立方体成绩外推复杂机器人或工业场景。

### 9.1 现状与缺口

| --- | --- |

### 10.5 模型与策略快速导入：放在哪个阶段（用户 2026-11-23 提出，评估）

用户希望把导入做成快速、便捷的功能：直接拖入 URDF；以后策略也一样；引导用户把文件放在哪里、如何导入资产包，导入后直接可用。M3 只做功能验证，这项先记录、不开发。评估如下：

| 部分 | 依赖 | 建议阶段 | 理由 |
| --- | --- | --- | --- |

### 10.6 策略推理：内置纯 C++ 推理核心（用户 2026-11-24 提出，D-111 已确定）

**现状：**M3 的预定义动作是“关键点 + 插值”，由命令队列按步执行，没有用到神经网络，也没有安装 PyTorch。

**用户的要求：**
- 以后的行走等策略可以快速导入；
- 推理集成在系统里，最好纯 C/C++，用户不用另装环境；
- 以后可以换用其他计算卡，甚至不用 CUDA。

**建议方案：**

| 层次 | 内容 | 阶段 |
| --- | --- | --- |
| 训练 | 在 Terra 之外（PyTorch、JAX 等），导出 **ONNX**；Python 接口的边界见 D-110 | M5 |
| 策略文件 | ONNX 模型 + 说明文件（JSON：观测由哪些量组成及顺序、缩放与偏移、动作对应的执行器、单位、控制频率、默认关节角、PD 增益）。拖入即用的向导核对这些映射（F-M5-06） | M5 |
| 推理核心 | Terra 内置、纯 C++、没有外部依赖：读取 ONNX（protobuf 格式由本项目自带的小解析器读取），执行机器人策略常用的算子：MatMul / Gemm、Add / Mul、ReLU / ELU / Tanh / Sigmoid / Softplus、Concat / Slice / Reshape / Transpose，以及 GRU / LSTM。CPU 执行，同一输入逐位相同。不支持的算子在加载时列出 | M5 前段（接口在 M4 末预留） |
| 加速后端（**用户要求后续必须支持**） | 推理接口设计为可替换的后端：CPU 内置核心为默认；后续接入 CUDA 与其他厂商（AMD ROCm、Intel OpenVINO、Vulkan 计算等），可经 ONNX Runtime 的执行提供程序或厂商库实现。现阶段只记录，不实现 | M5 之后按需排期 |
| 与仿真的衔接 | 策略作为 `SimulationRunner` 的每步控制器（M3-04a 已有接口），按控制频率降采样（例如物理 500 Hz、策略 50 Hz），输出目标关节角，交给 M3-04b 的 PD 层或位置执行器。观测来自快照与 M4 的传感器 | M5 |

**为什么不集成 PyTorch（libtorch）：**
- 运行库约 2 GB，并且绑定特定的 CUDA 版本，正是用户想避免的“装环境”；
- 机器人控制策略通常是几十 KB 到几 MB 的小网络，CPU 上每步推理只需微秒到毫秒，不需要完整的深度学习框架。

**先行验证（可在 M4 中安排一个小工作包）：**
- 用一个公开的 Go2 或 G1 行走策略（ONNX）检查算子清单；
- 比较内置核心与 ONNX Runtime 的输出（容差与耗时），结论写入 D-111。

### 10.7 资源库与索引：是否引入数据库（用户 2026-11-24 提出，D-112 已确定；实验记录在 M3-07 就进入 SQLite）

**现状：**场景、动作都是 `assets/` 下的 JSON 文件，通过“文件 → 打开”切换。2026-11-24 起，查看器的“动作”菜单会按当前场景列出 `assets/motions/` 中的预定义动作，这是扫描目录得到的，没有数据库。

**建议分两步：**

| 阶段 | 做法 | 理由 |
| --- | --- | --- |
| M3（现在） | 目录约定 + 打开场景时扫描 | 文件只有几十个，扫描在毫秒级；不增加依赖 |
| M4（随 F-M4-04 模型快速导入） | **资源库**：索引机器人、场景、动作、策略、环境贴图、导入的资产包；记录类型、名称、所属机器人、兼容场景、标签、来源与许可、sha256、缩略图；界面上提供“资源库”面板，可浏览、搜索、筛选、拖入。索引存于 **SQLite** | 导入的资产会越来越多，需要按机器人、标签、兼容性检索，并能发现文件被改动或丢失 |

**原则：**
- 文件是原件，数据库只是可重建的索引：删掉索引不丢任何东西，重新扫描即可恢复；版本管理和分享仍然针对文件。
- SQLite 是嵌入式 C 库：单个文件，不需要服务器和安装，公有领域许可，与“集成进系统、用户不用装环境”的方向一致。
- M3-07 的实验记录与 M5 的批量实验结果需要按条件查询，也可以存入同一套库；记录文件本身（JSON Lines）仍保留，便于查看与比较。

| # | 问题 | 建议 | 其他选项 |

| 1 | IMU 的计算方式 | **用 MuJoCo 自带的传感器**（加速度计、陀螺仪、姿态），经后端无关的接口读出。MJCF 中已有的直接用；场景文件给实体加 IMU 时，组合模型时插入安装点与传感器。加速度包含约束力的效果（MuJoCo 会为加速度计计算），比自己由速度差分更准 | Terra 自己由实体的位姿与速度计算（不依赖后端，但加速度要差分，接触时噪声大） |

| 6 | 坐标系名与 TF | 世界为 `world`，每个实体按“实例名/实体名”命名（如 `go2/base`），IMU 与相机各有自己的坐标系；相机图像坐标系按 ROS 约定（光轴为 z，图像向右为 x、向下为 y），与 Terra 相机坐标系（Z 向上）的换算集中在桥接模块里 | 只发布机器人基座，不发布全部实体（消息少，但外部不方便取连杆位姿） |

### 11.5 Sim-to-Real：通信层与真机一致（用户 2026-11-24 提出）

**目标：**外部程序（控制器、导航、感知）在仿真与真机之间切换时，**不改代码**，只改网络接口或域 ID。为此，仿真要在通信层模仿真机的驱动：

| 方面 | 要与真机一致的内容 |
| --- | --- |
| 话题与服务 | 名字、消息类型、方向（谁发布、谁订阅） |
| 消息内容 | 字段的含义、单位与符号、关节顺序、`frame_id`；厂商消息中的校验字段（如宇树 LowCmd 的 CRC，校验不对时真机会拒绝，仿真也拒绝） |
| 时间 | `header.stamp` 为采样时刻；发布频率与真机相同（如宇树 LowState 500 Hz、相机 30 Hz）；使用仿真时钟（`/clock`） |
| QoS | 可靠性、历史深度、持久性与真机驱动相同（传感器数据多为 best effort） |
| 中间件 | 与真机相同的 DDS 实现（宇树机器人使用 Cyclone DDS，仿真端用 `rmw_cyclonedds_cpp`） |
| 坐标系 | TF 树与真机的 URDF 一致（连杆名、相机与雷达的安装坐标系） |

**做法：按机器人配置“通信配置文件”（profile）。**桥接核心只有一个，每台机器人一份配置，说明发布哪些话题、用什么消息、多高频率、什么 QoS，以及命令从哪里来：

| 配置 | 适用 | 消息 |
| --- | --- | --- |
| 通用 | 任意机器人 | 只用 ROS2 标准消息（原 11.3 第 4～6 条的方案） |
| 宇树（Go2、G1） | 与宇树 `unitree_ros2` 一致 | 低层：`/lowstate`（`unitree_go/msg/LowState` 或 `unitree_hg/msg/LowState`，含 IMU、电机状态、足端力）与 `/lowcmd`（含 CRC）；高层运动服务另行评估 |
| Stretch 3 | 与 `stretch_ros2` 驱动一致 | `/joint_states`、`/stretch/cmd_vel`、轨迹动作接口、IMU 与 RealSense 相机话题 |
| TurtleBot 4 等 | 与其官方驱动一致 | 具体导入时再定（用户 2026-11-24） |

**真机话题清单：**每份配置附一份从官方驱动源码与文档整理的“真机话题清单”（话题、类型、频率、QoS、坐标系），与机器人模型一样按提交号锁定。验收时自动比较：仿真运行后的 `ros2 topic list -t`、`ros2 topic info -v`、实测频率与清单一致。

**做不到或不做的（逐项列出，不掩盖）：**
- 真机特有的硬件状态（电池、电机温度、错误码）：给出固定的合理值，在清单中标注“仿真值”；
- 厂商的高层运动接口（如宇树的步态 / 运动服务）背后是真机上的控制器，仿真里没有对应的控制器时不提供，在清单中标注；
- 网络延迟与丢包：P1 中可以配置（带种子），默认不加。

**对工作包的影响：**
- M4-05 增加“真机话题清单”的整理与锁定；
- M4-06 的桥接按配置文件组织，先做通用配置与宇树配置；
- 外部示例改为：同一个控制程序（读取 LowState、发送 LowCmd 让 Go2 站起与趴下）在仿真中运行；有真机时可在真机上原样运行。
- **需要用户准备：**宇树 `unitree_ros2` 的消息包（在 Humble 下编译，Cyclone DDS），以及 `ros-humble-rmw-cyclonedds-cpp`。具体命令在 M4-05 的说明中给出。
