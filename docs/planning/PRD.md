# EAI Terra 产品需求文档（PRD）

> 产品：**EAI Terra — An Open Robotics Simulation Engine**。M0 物理基础已全部验收，当前处于 M1 渲染基础阶段；平台窗口与输入系统已实现、待验收，实际网格渲染器尚未实现。需求完成度以[开发记录](DEVELOPMENT_LOG.md)为准，“已确定”仅指产品和技术方向。状态规则见[文档导航](README.md)。

## 1. 产品概述

### 1.1 背景与问题

机器人研发需要把模型、动力学、控制、可视化、传感器与外部算法组织为同一个可重复的实验环境。直接使用物理库仍需要补齐世界生命周期、资源映射、状态交换和机器人接口；依赖大型游戏引擎运行时又会引入引擎集成、发布和定制边界。

EAI Terra 计划构建独立、开放、可扩展的机器人三维物理仿真平台。以 MuJoCo 承担首代动力学求解，由 Terra 自己管理仿真世界、实体、时钟、场景、状态同步和渲染。开放性体现为明确的模块与数据接口；项目许可证仍待确定，不代表仓库已采用特定开源授权。

### 1.2 目标用户与使用任务

| 用户 | 需要完成的任务 | 产品应提供的结果 |
| --- | --- | --- |
| 机器人算法与控制工程师 | 加载模型、施加控制、检查运动与接触 | 可复现状态、明确单位与时间、可自动回归的实验 |
| 具身智能与训练研究者 | 批量执行 reset/step/观测与策略评估 | 可脱离图形运行的物理环境；后续 Python 接口 |
| 工业仿真与数字孪生工程师 | 组织设备、环境与机器人，呈现运行状态 | 场景与资产映射、实时可视化、外部系统接口 |
| 引擎与工具开发者 | 扩展传感器、渲染或物理适配 | 不泄露后端结构的数据契约和可独立验证的模块 |

### 1.3 产品定位与核心价值

| 对象 | 在本项目中的定位 | Terra 的责任边界 |
| --- | --- | --- |
| MuJoCo | 首个物理计算后端，使用其官方 C API | 物理能力通过适配层接入；MuJoCo 的模型结构不等于 Terra 的世界与场景架构 |
| Unity / UE5 | 通用实时内容与应用引擎，可作为行业参照 | Terra 不依赖其运行时；不在首期追求复制其编辑器和完整内容生态 |
| EAI Terra | 面向机器人应用的独立仿真引擎 | 掌握世界管理、物理接口、状态交换、渲染和机器人扩展接口 |

核心价值是：同一物理能力既能用于自动化实验，也能被独立渲染器和机器人应用消费；物理状态与美术资产有明确映射；版本、输入与观测可记录，失败可以定位到具体边界。

## 2. 产品目标与成功判据

| 目标 | 可检验的产品结果 | 首次覆盖阶段 |
| --- | --- | --- |
| 自主可控的机器人仿真平台 | Terra 控制运行生命周期与公共接口，不依赖游戏引擎运行时 | M0 起持续约束 |
| 物理计算与图形渲染解耦 | 不创建图形上下文也能完成物理验收；渲染只消费 Terra 状态 | M0 / M2 |
| 支持机器人与复杂物理场景 | 从基本刚体到受控机器人，再到一个有任务定义的工业示例 | M0 / M3 / M5 |
| 高质量实时三维可视化 | 从基础显示到材质、光照和阴影；按固定场景和硬件验收 | M1–M5，画质与性能尚待验证 |
| 支持传感器与算法扩展 | 传感器输出带时间和坐标信息；ROS2/Python 不侵入物理核心 | M4 / M5 |

不以画面观感替代接触精度、控制正确性或传感器真实性验证；不宣称当前已有机器人、训练或工业场景能力。

## 3. 分阶段功能需求

优先级按阶段解释，定义见[文档导航](README.md)。本表维护需求定义，实际实现状态统一见开发记录；工程骨架已建立不等于对应物理需求已验收。具体模块、接口和测试方法分别见[技术设计](TECHNICAL_DESIGN.md)与[开发计划](DEVELOPMENT_PLAN.md)。表中的验收条件是将来需满足的要求，不是已取得的结果。

### 3.1 M0 — 基础工程与 MuJoCo 物理集成

| 编号 / 优先级 | 功能描述 | 输入 → 输出 | 依赖条件 | 验收标准 |
| --- | --- | --- | --- | --- |
| F-M0-01 / P0 | 建立 C++17 工程与官方 MuJoCo 依赖边界 | Ubuntu 22.04、GCC、CMake、Ninja、候选库 → 可复现的纯物理目标及版本记录 | 无；版本先验证后锁定 | 干净构建与运行路径明确；无窗口库或图形上下文前置条件；版本兼容证据可追溯 |
| F-M0-02 / P0 | Headless 程序加载 MJCF 并管理生命周期 | MJCF 路径、运行参数 → Terra 世界实例或明确错误 | F-M0-01 | 无图形会话下成功加载立方体场景；缺失或损坏模型以非零退出码结束，不崩溃 |
| F-M0-03 / P0 | 固定步进、重置与最小控制入口 | 固定步长、步数、可选控制 → 推进后的仿真状态 | F-M0-02；控制适配 | 完成自由落体和碰撞稳定测试；reset 可重复；简单关节夹具验证控制维度和非法输入处理 |
| F-M0-04 / P0 | 输出位置、姿态、关节与相关物理状态，提供后端无关快照 | 已初始化状态 → 时间、位姿、速度、关节状态、接触摘要、诊断 | F-M0-02 / F-M0-03 | 输出包含单位、坐标约定和实体标识；数据有限且时间一致；应用不接触 MuJoCo 类型；旧快照不随下一步变化 |
| F-M0-05 / P0 | 自动化正确性、失败路径与回归验收 | 固定夹具、参数和版本 → 机器可判定结果与验证报告 | F-M0-01–04 | 满足开发计划的 M0 验收基准和 DoD，记录证据；全程无 OpenGL 上下文 |

| 编号 / 优先级 | 功能描述 | 输入 → 输出 | 依赖条件 | 验收标准 |
| --- | --- | --- | --- | --- |

| F-M1-02 / P0 | 基础材质、光照及资源加载最小路径 | 测试网格与材质 → 可重复的渲染示例 | F-M1-01；资产格式初版约定 | 显示指定测试资产，资源缺失可诊断；渲染公共接口不接收 MuJoCo 类型；glTF/GLB 优先方案仍待验证 |

### 3.3 M2 — 物理与渲染同步、场景系统

| 编号 / 优先级 | 功能描述 | 输入 → 输出 | 依赖条件 | 验收标准 |
| --- | --- | --- | --- | --- |
| F-M2-01 / P0 | Terra 场景实例、稳定实体标识与物理/视觉映射 | 场景描述、物理模型、视觉资产 → 场景实例和映射诊断 | M0、M1；初版场景表示与 ID 规则 | 同一实体的多视觉部件正确关联；同名不同实例不串扰；缺失映射可定位 |
| F-M2-02 / P0 | 用状态快照驱动独立渲染，解耦时间步与帧率 | 带时间和世界代次的快照、渲染时钟 → 一致的物体姿态 | F-M2-01；M0 快照契约 | 同一控制序列在不同渲染帧率下产生容差内一致的物理轨迹；reset 不插值到旧世界；渲染器只读取 Terra 数据 |
| F-M2-03 / P1 | 场景浏览、暂停/继续及基础加载验证 | 运行命令、场景描述 → 状态变化与诊断 | F-M2-01 / F-M2-02 | 可重建一个小型场景，暂停时物理时间不增长；此处不要求完整图形编辑器 |

## 4. 非功能需求

| 编号 | 维度 / 优先级 | 要求与验收方式 |
| --- | --- | --- |
| NFR-01 | 模块解耦 / 各阶段 P0 | Core/Scene 公共契约不暴露 `mjModel`、`mjData` 或 OpenGL 类型；MuJoCo 依赖限制在后端；纯物理目标不要求窗口或上下文。通过依赖审查、构建和无显示环境运行验证 |
| NFR-02 | 正确性与稳定性 / M0 P0 | 立方体、重置、关节和错误路径满足开发计划基准；状态为有限数、姿态归一化；连续运行与循环生命周期不崩溃、不静默重置。当前无测试结果 |
| NFR-03 | 性能 / M0 记录基线，后续 P1 | 记录物理步耗时、实时因子、输出开销、内存；M1 起记录帧耗时。候选目标是简单场景实时因子 ≥ 1、基础画面 60 FPS，**尚未测量且不构成已实现性能或 M0 阻塞门槛**；必须先固定硬件、分辨率、场景、步长与统计方法再确认 |
| NFR-04 | 可扩展性 / 各阶段 P0 | 新增渲染消费者或外部桥接不需访问 MuJoCo 结构；M0 通过虚拟快照消费者验证边界，无需实现第二物理后端或插件框架 |
| NFR-05 | 跨平台性 / M0 P0，扩展 P2 | 首期仅承诺验证 Ubuntu 22.04 / x86-64 / GCC / C++17；Windows、macOS、ARM 均为后续候选，不能标为已支持；平台差异限制在相应适配模块 |
| NFR-06 | 可测试性 / 各阶段 P0 | 物理测试可命令行执行、返回机器可识别结果；模型、版本、参数与容差随报告记录；图形测试单独启用，不阻塞无图形物理测试 |
| NFR-07 | 可复现性 / M0 P0 | 同模型、版本、编译选项、初始状态、控制序列和种子下按容差回归；不承诺跨 CPU、后端或版本逐位确定性；快照用于观测，不宣称可完整恢复求解器内部状态 |
| NFR-08 | 可诊断与可维护 / M0 P0 | 加载、参数、控制和数值异常包含上下文；后端严重错误的进程行为有明确约定；构建方式、依赖版本和报告入口可追溯 |

候选性能目标和数值测试容差属于不同概念：性能用于建立基线；数值容差用于预先定义正确性边界，首次兼容验证后应连同理由冻结，不得测试失败后无说明放宽。

## 5. MVP 范围

**MVP = M0 的最小物理仿真闭环。** 它包含基础工程、经验证后锁定的 MuJoCo 官方库、MJCF 加载、固定步进、reset、最小控制入口、Terra 状态与快照、立方体碰撞稳定及自动化验收。

第一个可运行示例必须是：立方体从空中自由下落，与地面碰撞后稳定，输出仿真时间、位置、姿态、速度和接触等相关状态。初始场景不含机器人或执行器；随后以简单关节夹具验证状态读取和控制接口。全程不创建 OpenGL、EGL 或 OSMesa 上下文。

MVP 不包含窗口、三维编辑器、GLB 渲染、PBR、复杂视觉效果、传感器、ROS2、Python 绑定、强化学习框架、复杂工业环境、多线程执行或多物理后端实现。接口只为后续保留边界，不能将后续能力追加为 M0 的隐性前置条件。

## 6. 阶段推进与验收归属

阶段顺序为 M0 → M1 → M2 → M3 → M4 → M5。各阶段 P0 通过并记录 DoD 证据后再启动下一阶段。P1/P2 可递延，但需记录原因和影响，不能掩盖未完成的 P0。

本文件维护“产品需要满足什么”；任务步骤、数值验收基准与完成定义以[开发计划](DEVELOPMENT_PLAN.md)为准；模块与接口语义以[技术设计](TECHNICAL_DESIGN.md)为准；尚未定案的技术选择以[决策记录](DECISIONS.md)为准。
