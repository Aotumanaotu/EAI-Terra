## 3. 状态与优先级约定

决策状态与实现状态是两个维度：**“已确定”不等于“已实现”，“暂定”不等于“已验证”。**

- 决策状态使用：已确定、暂定、待讨论、已废弃，以 [DECISIONS](DECISIONS.md) 为准。
- 实现状态使用：未开始、进行中、待验收、已验收；新增任务默认“未开始”。“已验收”必须有对应提交、环境、执行步骤与测试证据。
- 验证状态使用：未验证、验证中、通过、未通过。候选版本、性能目标和数值容差在取得证据前始终标记为“候选／尚待技术验证”。
- P0：对应阶段完成的必要条件；P1：该阶段核心条件满足后推进；P2：后续增强。不同阶段的 P0 不表示现在可以越过 M0 提前开发。

## 4. 需求、设计与任务如何对应

PRD 为需求编号 `F-M阶段-序号` 和非功能需求编号 `NFR-序号`；开发计划使用 `M0-01` 等任务编号，并关联 PRD；设计解释这些需求如何由模块和数据契约承接；决策用 `D-序号` 记录选择理由。

例如：PRD 的 `F-M0-02` 要求 Headless 加载 MJCF → 开发计划 `M0-03/M0-04` 安排实现与验收 → 技术设计约束加载生命周期和适配层 → `D-002/D-006/D-007` 说明为何使用官方库、先做无图形仿真且不改内核。

单一事实只设一个主要维护位置：需求范围在 PRD，实施步骤和测试数值在开发计划，数据和接口语义在技术设计，方案状态在决策记录，实际实现状态与验证证据在开发记录。其他文档引用它，不复制大段内容。

## 5. 更新规范

1. 先检查现有编号和关联文档，整合已有内容；不重用已删除或废弃条目的编号。
2. 需求变更先更新 PRD 的范围与验收，再同步任务、设计和受影响决策；架构变更先记录决策背景，再同步设计、任务和根 README。
3. 暂定方案升级为已确定时记录确认依据；涉及兼容性、正确性、性能的结论还必须附实际验证证据。不能凭计划文字将实现状态改为已验收。
4. 方案废弃时保留原编号、原因与替代条目，不静默删除历史。本次“渲染优先”路线的替换记录在 `D-901`。
5. 任务或验收报告记录日期、代码提交、操作系统、编译器、依赖精确版本、模型摘要、参数、执行方式与结果。未来的验证报告放在 `docs/validation/`，当前不创建空报告或伪造结果。
6. 每次文档修改检查相对链接、需求与任务的对应关系、阶段范围、状态用词和根 README 一致性；本轮不以编译或仿真测试替代文档检查。
7. 进入下一阶段前评审上一阶段 Definition of Done、未关闭风险及需求变更。后续阶段的工作量在阶段启动时重新估算。
8. 每次实际开发同步更新开发记录；将完成内容、失败结果和未执行项分别写清。文档计划或环境配置不能计作引擎功能已验收。
