# EAI Terra 技术决策记录

> 本文记录选择的状态与理由，不记录虚构的实现结果。当前已有 M0-01 工程骨架，M0-02 依赖集成已通过基线验证、待验收，物理仿真和渲染功能尚未实现；实际进度见[开发记录](DEVELOPMENT_LOG.md)，变更规则见[文档导航](README.md)。

## 1. 状态与决策规则

- **已确定：**当前开发必须遵守的方向；不表示已经实现或验证。
- **暂定：**有优先候选、可用于原型验证，但尚未形成最终接口或方案。
- **待讨论：**需要明确条件、比较备选并作出选择，不能写成默认已采用。
- **已废弃：**被明确替换的旧方向，保留背景和替代记录。

每条条目包含编号、主题、当前状态、背景原因、选择或备选、影响范围。升级状态时补充确认依据；涉及技术有效性的结论必须关联报告。当前已确定条目的依据为本次明确的项目方向及与其一致的原 README；暂定条目是从原 README 或本轮设计提案提取的候选，均无验证通过证据。

| D-004 自研渲染与首个 API | 已确定，未实现 | 需要掌握渲染、资产和机器人显示链路 | 自研 Terra Render，OpenGL 先行；不使用 MuJoCo 自带渲染器作为最终方案；Vulkan 不在首期并行实现 | Render、M1 以后 |

| D-008 首期语言与开发基线 | 已确定，工程基线已建立、M0-01 待验收 | 统一初期环境，降低跨平台变量 | Ubuntu 22.04 / x86-64、C++17、GCC、CMake、Ninja；工具精确版本与既有验证结果见 M0-01 验证记录 | 工程、验证、开发计划 |
| D-009 Terra 公共接口独立 | 已确定，未实现 | 避免后端数据结构成为全项目事实标准 | 上层不得直接依赖 `mjModel/mjData` 或其索引；Terra 负责 ID、时钟、状态与映射，适配层负责转换 | 公共 API、Scene、Bridge、Render |

## 3. 暂定

| 编号 / 主题 | 当前状态 | 背景与原因 | 优先建议 / 尚需验证 | 影响范围 |
| --- | --- | --- | --- | --- |
| D-011 Physics 接口形态 | 暂定，已实现（M0-07），基线机器验证通过 | 需要先明确最小操作，再用原型校正语义 | M0-07 评审（2026-11-17）：抽象基类 `terra::physics::PhysicsWorld` + 后端入口 `mujoco::loadWorld`；`loadModel+initialize` 合并为原子 `load`，`getState` 并入 `snapshot()`；`setControl` 按执行器 ID 部分更新、原子、越界拒绝；错误用返回值。M1 起 Core 需要外部绑定时可再拆分 load/initialize；ABI 与配置格式未冻结。见 [M0-07 报告](../validation/M0-07-physics-interface.md) | Physics、Headless、后续 Bridge |
| D-012 初版状态与发布模型 | 暂定，已实现，开发机与基线机器验证通过（M0-06） | 先消除坐标、时间与所有权歧义，再优化线程和复制成本 | 建议 SI、右手 Z-up/X-forward/Y-left、双精度、wxyz；M0 单线程复制不可变快照；初始化/reset/步后先完整刷新派生量；由 M0-06/07 验证冻结 | Core、PhysicsSnapshot、Render 与测试 |
| D-013 视觉资产优先格式 | 暂定，未实现、未验证 | 原 README 提出 glTF/GLB 优先，便于与建模工具衔接 | 优先评估 glTF/GLB；导入库、扩展支持、单位/轴向转换和材质范围待 M1 验证；不能视为统一场景格式 | Render、Scene、资产制作 |
| D-014 ROS2 初期发行版候选 | 暂定，未实现、未验证 | 原 README 提到初期面向 Humble，需结合实际接入环境核查 | Humble 为候选；版本、部署环境、消息和进程边界在 M4 前评审，不将其写入 Core 前置依赖 | Bridge、M4、环境矩阵 |
| D-015 依赖与测试集成方式 | 暂定，已实现，基线机器验证通过（M0-02） | 需要可复现构建，避免隐式联网与额外框架先行 | 显式本地安装路径 `MUJOCO_ROOT`（默认 `third_party/mujoco/install`）；CTest 入口。官方 `mujocoConfig.cmake` 无条件依赖 OpenGL，因此**不用 `find_package`，直接加载官方导出的 `mujocoTargets.cmake`**（即“隔离的导入目标”），并按 `mujoco.lock` 核对版本；运行库查找使用构建树 RPATH。只有获取源码和首次构建 MuJoCo 时联网，Terra 构建不联网。见 [M0-02 报告](../validation/M0-02-mujoco.md) | M0-01/02/09、构建与交付 |
| D-016 M0 数值基准与容差 | 暂定，未验证 | 正确性需要可判定输入和门槛，但当前没有测量 | 立方体配置与候选容差集中见开发计划；固定环境验证后冻结；性能候选目标不作为 M0 已通过结论 | M0-08/09、测试资产与报告 |

## 4. 待讨论

| 编号 / 主题 | 当前状态 | 背景与原因 | 备选与需要回答的问题 | 影响范围 / 最迟决策点 |
| --- | --- | --- | --- | --- |
| D-101 OpenGL / Vulkan 长期演进 | 待讨论 | 首个 API 已定，但没有测得长期图形瓶颈 | 保持 OpenGL；在瓶颈出现后加 Vulkan；或逐步替换。需比较硬件覆盖、性能证据、维护成本和必要抽象；不预先实现完整通用图形层 | Render；M1 建基线，新增后端前决策 |
| D-102 场景数据格式 | 待讨论 | MJCF 与 glTF 分别描述物理和视觉，不能直接代替 Terra 世界描述 | Terra 清单引用物理/视觉资源，或评估标准场景描述；JSON/YAML 等编码只是候选。需明确实例、绑定、版本、相对路径、持久 ID 与导入边界 | Scene、工具、资源；M2 前形成最小方案 |
| D-103 实体组件系统 | 待讨论 | 世界需要稳定实体和关系，但没有复杂度证据要求完整 ECS | 简单注册表与显式关系、轻量组件组合、成熟 ECS 库。需比较访问模式、所有权、序列化、调试和开发成本；M0 只做最小 ID 映射 | Core、Scene；M2 前评审，M0 不受阻 |
| D-104 ROS2 接入方式 | 待讨论 | 时间、消息、执行器与进程边界会影响仿真调度 | 可选进程内桥接或独立进程通信；需明确仿真时钟、TF、命令时序、QoS、暂停/reset、消息契约及依赖隔离 | Bridge、Sensors；M4 前 |
| D-105 机器人模型与渲染资源统一管理 | 待讨论 | 连杆、geom、网格、碰撞形状和资源实例不总是一一对应 | 显式映射清单、导入时生成描述、资源数据库等候选；需明确原点、尺度、许可、缓存、机器人重复实例和 URDF 导入支持范围 | Scene、Physics、Render；M2 初版，M3 复核 |
| D-106 多线程仿真架构 | 待讨论 | 固定物理频率与显示/传感器频率不同，但未测得线程需求 | 单线程调度、物理/渲染双线程、进一步任务化；比较不可变引用、队列、双/三缓冲，定义命令边界、背压和重置屏障 | Core、Render、Sensors；M0 后按测量决定 |
| D-107 多物理后端支持方式 | 待讨论 | 后端差异不只是 API 名称，不应过早承诺语义兼容 | 单实现接口、编译时选择、运行时工厂或插件；需以第二后端真实需求定义能力查询、模型导入、控制、状态与容差差异 | Physics、Scene、构建；第二后端需求成立后 |
| D-108 MuJoCo 精确版本与交付 | **已确定：4.0.1 已锁定**（2026-11-18，M0-09） | 仓库没有版本锁定、官方包或兼容证据 | **获取方式：官方源码构建**（用户决定，2026-11-13，便于后续修改），源码包 sha256 校验，仅构建核心库，用 gcc-12 编译。**锁定版本 4.0.1**：M0-02 基线验证、M0-04–08 物理回归与第三方许可核查均已完成（锁定条件见 [M0-02 报告](../validation/M0-02-mujoco.md) 第 5 节，核查见 [M0-09 报告](../validation/M0-09-acceptance.md)）。记录见 `third_party/mujoco/mujoco.lock`。升级须重跑 `scripts/verify/m0_acceptance.sh` 并重新评审 M0-08 冻结的容差 | 版本升级时复核 |
| D-109 项目许可证 | 待讨论（第三方库核查已完成） | 原 README 明确 TBD，开放定位不能代替授权条款 | 核查项目、第三方库、模型和资产的授权及再分发要求后选择；本轮不新增未经确认的许可证。M0-09 核查：MuJoCo（Apache-2.0）及其 7 个构建依赖均为宽松许可、无 copyleft，分发时需保留版权与许可声明（qhull 要求随二进制附带其 COPYING.txt），见 [M0-09 报告](../validation/M0-09-acceptance.md) 第 3 节。项目自身许可证仍由用户决定；当前测试夹具均为本项目自写 | 发布、资源使用与贡献；分发前 |

## 6. 决策如何落地

1. 方案变更先记录背景、备选、边界与影响，必要时引用实际验证报告。
2. 更新本表状态，同时同步[技术设计](TECHNICAL_DESIGN.md)、[开发计划](DEVELOPMENT_PLAN.md)及受影响的[PRD](PRD.md)条目。
3. 在[开发记录](DEVELOPMENT_LOG.md)记下实现任务、提交和验证结论。决策成立与实现通过分别记录。
4. M0 开发前优先处理 D-108 和 D-015；场景格式、ECS、ROS2、Vulkan、多线程、多后端等讨论不成为 M0 预先实现完整框架的理由。
